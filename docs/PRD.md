## 1. 背景与问题

办公场景中存在大量高频、重复的表格处理工作：多表核对（对账）、数据清洗（查重 / 补全）、批量填报（按行情回填价格）。

- **人工处理**：耗时、易错，且难以留痕。
- **现有 AI 工具**：多为"黑盒式"单轮生成，结果不可追溯、缺乏校验，一旦编造数据无人察觉；所有决策都走大模型，成本不可控。

**核心矛盾**：用户需要的是"可信、可追溯、成本可控"的自动化，而不是"看起来很快"的自动生成。

## 2. 产品定位与目标

**定位**：一句话输入办公数据处理需求，系统自动完成"规划 → 查数 → 执行 → 校验 → 报告"全流程。

**设计原则**：**LLM 只做决策，代码守底线**（实际读写、校验、预算、溯源全部由代码完成）。

**目标**：
1. 结果可信——关键判定由确定性代码完成，杜绝编造；
2. 成本可控——全局 Token 预算，实时分账，超限熔断；
3. 可交付——输出可溯源报告 + 可回放轨迹。

## 3. 目标用户与使用场景

| 用户 | 场景 |
|---|---|
| 财务 / 采购 | 银行流水与台账对账，输出差异清单 |
| 行政 / HR | 名单去重、缺失字段补全 |
| 项目 / 助理 | 报价表、物资清单按最新行情批量填报 |

## 4. 名词定义

| 名词 | 说明 |
|---|---|
| Agent | 承担单一职责的智能体，本系统共 5 个 |
| Orchestrator | 编排器，状态机调度各 Agent，不直接操作文件 |
| Blackboard | 共享黑板，Agent 间唯一的状态交换通道 |
| Verifier | 校验 Agent，**纯代码**判定，不调用大模型 |
| 场景模板 | 可插拔的业务配置（对账 / 清洗 / 填报） |
| 确定性校验 | 由代码规则给出的校验结论，可复现 |

## 5. 产品范围

**做**：Excel 表格的读取、比对、查重、补全、批量填报；报告生成；成本与轨迹可视化；对账 / 清洗 / 填报三类场景。

**不做**（本期）：删除数据行等破坏性操作；多租户与云端部署；训练/微调模型。

## 6. 总体架构

```
接入层     WebUI（两步式审批 + 实时轨迹 + 成本面板） / CLI / MCP Server
编排层     Orchestrator 状态机 + Blackboard 共享状态 + Trace 轨迹 + Budget 预算
Agent 层   Planner · Retrieval · Executor · Verifier · Reporter
工具层     Registry（20 个工具）：Excel 读写 / 比对查重 / 联网检索
场景层     scenarios/*.json（换场景零代码）
```

## 7. 功能需求

| 编号 | 功能 | 描述 | 优先级 | 验收标准 |
|---|---|---|---|---|
| FR1 | 场景模板 | 对账 / 清洗 / 填报，配置化切换 | P0 | 换场景不改代码即可运行 |
| FR2 | 任务规划 | 扫描目录、读取结构、生成执行计划 | P0 | 计划含目标文件、关键列、比对列、步骤 |
| FR3 | 人工审批 | 生成计划后经用户确认才执行 | P0 | 未确认不得写文件；可取消 |
| FR4 | 数据检索 | 需要外部数据时联网查询，每条带来源 | P1 | 检索不到标注 not_found，禁止编造 |
| FR5 | 执行 | 写入 / 比对 / 查重（工具化，非心算） | P0 | 写操作前自动备份；结果可复核 |
| FR6 | 确定性校验 | 完整性 / 溯源 / 一致性 / 查重 | P0 | 由代码给出结论，不调用 LLM |
| FR7 | 重规划 | 校验失败时携带失败项回到 Planner | P1 | 默认 1 轮，可配置上限 |
| FR8 | 报告 | 生成可交付的 markdown 执行报告 | P0 | 含结论、差异明细、数据来源、成本 |
| FR9 | 预算护栏 | 全局 Token 预算，超限熔断 | P0 | 超限即停并如实记录，报告仍生成 |
| FR10 | 可观测 | 每步轨迹 + 各 Agent 成本分账 | P1 | 运行记录落盘，可回放 |
| FR11 | 并行执行 | 多文件线程池并处理 | P2 | 结果与串行一致，且更快 |
| FR12 | MCP Server | 工具层以标准 MCP 协议对外暴露 | P2 | 外部 Agent 可调用同一套工具 |
| FR13 | 数据溯源 | 每条写入值记录来源与置信度 | P0 | 报告可列出"条目 → 值 → 来源" |

## 8. 非功能需求

- **成本**：对账任务平均 < 3 万 tokens；超预算自动停止。
- **安全**：API Key 仅来自 `.env`；写操作前备份；可选写沙箱（仅允许写 data 目录）；防公式注入；WebUI 防 XSS。
- **可靠**：单文件失败隔离；LLM 未写入时由代码确定性兜底。
- **可维护**：确定性内核与 LLM 解耦，14 项自动化测试（Mock LLM 零成本验证）。

## 9. 核心流程

**主流程**：用户任务 → 选择场景 → 规划 → 人工审批 →（按需检索）→ 执行 → 校验 → 报告。

**重规划流程**：校验不通过 → 携带失败项回到规划 → 重新执行 → 再次校验（默认最多 1 轮）。

```
规划 → 审批 → 检索? → 执行 → 校验 ──通过──→ 报告
                 ↑              │
                 └──── 重规划 ───┘（不通过且未超轮数）
```

## 10. 数据结构（黑板）

| 分区 | 内容 |
|---|---|
| plan | 目标文件、关键列、比对列、步骤 |
| approval | 是否确认、是否允许参考数据 |
| collected | 检索结果（item / value / source / confidence） |
| writes | 写入记录（文件 / 行 / 值） |
| verifications / findings | 校验结果与问题清单 |
| diff / duplicates | 比对与查重结果 |

## 11. 验收标准（DoD）

1. 一句话任务可在无人工干预下产出报告（对账 / 清洗 / 填报三场景各跑通）；
2. 校验结论由代码给出，报告含数据来源；
3. 预算超限能熔断且报告不丢；
4. 写操作前均有备份；
5. 换场景只需改 JSON。

## 12. 量化指标（真实评测）

| 任务 | 多 Agent | 单 Agent 基线 | 结论 |
|---|---|---|---|
| 多表核对 | 3/3 成功，平均 29,344 tokens | 3/3 成功，平均 81,429 tokens | **成本 −64%** |
| 数据清洗 | 3/3 成功，平均 31,732 tokens | 3/3 成功，平均 32,777 tokens | 持平 |
| 并行写多文件 | 17 文件 / 281 项，1.22s | 串行 2.07s | **提速 ≈1.7×** |

> 注：基线无独立校验环节，其"正确"不可验证；v2 结论由确定性校验背书。

## 14. 风险与边界

- **联网检索质量**：中文行情站点抓取不稳定，查不到时如实标注（不编造）；演示可用内置参考数据兜底。
- **SSRF / 提示注入**：`fetch_web` 存在抓取任意 URL 的面，网页内容可能诱导写操作；已用确定性校验 + 沙箱 + 人工审批缓解，生产需域名白名单与鉴权。
- **并发**：Agent 间通过黑板串行协作，不做并发写黑板；仅文件级并行。
- **非生产级**：本期无多租户、无云端部署、无监控告警。
